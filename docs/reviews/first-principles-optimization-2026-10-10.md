# 从使用目的重建 Codex Router 的优化边界

日期：2026-10-10。基线运行代码：`00eed6eb9f894a734eb51bb2e2b058575c6dca7a`。
本报告区分代码复现、运行观察、解释和未验证假设。实现先在个人 fork 验证，尚未替换生产服务。

## 能证实的结论

项目确实存在可删除的工作、过宽的故障依赖和不准确的成功统计。不能据此证明“协作者多”是原因，也不能把所有网络故障归因于 Router。

最近 100 个 PR 的样本中，84 个合并，81 个没有正式 review 记录，58 个没有正式 review 或 issue comment；当前上游 main 没有强制状态检查。这个样本来自一次集中清理积压的时期，不能外推长期缺陷率。评论中的复现、负向对照和取舍讨论也是审核证据，不能因为没有 APPROVED 就认为无人审核。已有三系统 Node 测试、原生应用测试、Electron 构建和锁定 Python 安装验证，不能称为“只有简单测试”。[上游分支](https://github.com/duolahypercho/codex-router/tree/00eed6eb9f894a734eb51bb2e2b058575c6dca7a)、[积压审查记录](https://github.com/duolahypercho/codex-router/blob/00eed6eb9f894a734eb51bb2e2b058575c6dca7a/docs/reviews/pr-backlog-2026-10-10.md)、[PR #986](https://github.com/duolahypercho/codex-router/pull/986)、[PR #994](https://github.com/duolahypercho/codex-router/pull/994)。

更符合已知证据的解释是：个人使用的少数路径承担了大量通用兼容责任，而输出、生成状态、路由依赖和发布时序没有始终使用同一份判断。作者数量只能作为待验证变量。

## 方法：先确定不可违背的事实

马斯克谈第一性原理时，强调从基础事实重新推导，而非沿用相似系统的做法。五步顺序是质疑需求、删除部件或过程、简化剩余部分、缩短周期、最后自动化。这里采用的是推理顺序；访谈中的删除比例提示不是软件必须删掉某个百分比的验收规则。[TED 访谈](https://www.ted.com/talks/elon_musk_the_mind_behind_tesla_spacex_solarcity)、[Starbase 原访谈，约 13:30 起](https://www.youtube.com/watch?v=t705r8ICkRw&t=810s)。

对本系统，基础约束是：

1. 用户需要在同一客户端选择原生和自定义模型，保留工具、历史、图片、压缩和取消语义。存在某种官方自定义配置，不等于已经证明它能提供相同的桌面体验。
2. 已执行的远程计算不能靠关闭本地连接撤销。客户端未收到字节，也不能证明上游未接收 POST。重试不是免费恢复。
3. HTTP 200 只说明该跳点接受了 HTTP 响应，生成仍可能失败、不完整或没有终止事件。令牌消耗与生成成功是不同维度。
4. 协议转换只有在两端确实不兼容时才有必要。相同协议仍可能有认证、工具命名、帧验证和厂商字段差异，不能直接把全部中间层删掉。
5. 数据、权限、进程内采用的配置和客户端目录必须属于可解释的同一代状态。磁盘写入和进程采用是两件事。
6. 用户隐藏的模型可能仍被历史会话、别名或视觉辅助调用；缺少凭据不等于用户撤销了选择。
7. 对性能的判断必须区分本地工作和远程等待。减少一个进程或一次 ACL 操作，不等于模型生成速度提高相同比例。

优化目标据此定为：降低得到一个正确、完整结果的总成本，以及失败时的恢复成本。成本包括延迟、额外生成、内存、配置漂移、诊断时间和维护负担。不能单独追求请求次数少、代码行数少或 HTTP 成功率高。

## 第一步：质疑需求及其隐含前提

| 既有做法背后的前提 | 验证结果 | 应保留的真实需求 |
| --- | --- | --- |
| 所有模型都需要 LiteLLM | 错。原生 GPT 和经契约测试的 HTTP Responses 路径不需要它；Chat、Messages 和专用适配仍可能需要 | 按具体模型的有效协议构建执行计划 |
| 容器 provider 相同，协议就相同 | 错。逐模型 endpoint 和协议 variant 可以覆盖容器默认值 | 解析最终模型，而非仅看 provider 名字 |
| 菜单隐藏就可以停止依赖 | 错。隐藏不禁止历史会话或辅助调用 | 包含全部可调用路由，显示策略另算 |
| 未配置的 provider 应自动删除 | 不成立。会抹掉明确选择，也使以后补凭据行为难解释 | 保留选择并返回具体设置错误 |
| 无输出的 502/reset 可以安全重复 | 错。模拟上游完整消费 POST 后断开，基线再次提交 | 只有明确未发送的错误可默认重试；不确定重放需要显式策略 |
| 连接拒绝总证明整个尝试未发送 | 有条件。307/308 的第一站已消费 POST，下一站才拒绝连接 | 生成请求拒绝重定向，不能把第二站的失败当作第一站未发送 |
| 上游 JSON 的 not_sent 字段可信 | 错。响应体和原站伪造的头不能授权重放 | 只信实际本地 API 服务产生的运输证据；原站同名头被剥离 |
| HTTP 200 可以计为成功 | 错。response.failed、不完整流都可发生在 200 内 | 明确记录生成终态并保留全部已知用量 |
| Responses WebSocket 只会收到 response.create | 已失效。官方 Codex 的 steering 已发送 response.interrupt；本机二进制包含该协议，旧路由器的拒绝语句与实际报错完全一致 | 中断消息绕过生成队列、结束当前响应并保留同一连接的续接能力 |
| reasoning 标签总是私密思考泄漏 | 错。代码、XML 示例和截断标签也合法 | 默认保真；只给有证据的具体模型启用修复 |
| Windows rename 后必须再做相同 ACL | 常规文件不需要；备份、恢复、外部文件是不同对象 | 一个经过验证的私有写入边界，保留必要的 fsync 和生命周期保护 |
| 扫描所有可选提供商更利于诊断 | 默认诊断中会淹没当前配置问题 | 默认检查相关配置，完整盘点使用 --all |
| 目录刷新越频繁越可靠 | 不成立。账户和客户端变化有事件；服务器发模型没有本地事件 | 事件触发、合并重复工作，以及每日兜底 |
| 发布目录即完成启用 | 错。运行进程可能仍持有旧 registry 或没有对应监听器 | 先准备依赖、采用并验证，再发布客户端 |
| 停止 Router 和依赖可同时进行 | 错。依赖先停会切断尚未完成的流 | 先停止入口接单并排空，再停止依赖 |
| formal review 数量等于审核质量 | 不成立，已有反例；无强制门禁则确实可以绕过检查 | 验证具体行为及失败对照，再决定采用 |

每项需求的责任主体应对应到实际接口和验收行为：用户决定显示、提供商与网络决定远程能力，Router 负责本地协议和交付语义，安装器负责配置与服务采用，维护者负责合并验证。不能把“以前一直这样”作为独立需求。

## 第二步：删除有反证支持的工作

已实施的候选改动包括：

- 正常 Responses 输出默认保留原文；已知旧模型泄漏使用明确的模型级策略。包括行内 XML、代码块、UTF-8 分块和末尾不完整标签的对照测试。
- 在 GLM/Grok 等已验证的 Responses 路径删除 Python 协议转换这一跳，保留 Node API 的凭据解析、请求准备、工具恢复和帧验证。
- 不启动未被执行计划使用的 OAuth 服务。原生路径先获得核心可用性，缺失网关时可继续服务独立路径，完整 readiness 保持失败以阻止错误发布。
- 24 个私有写入实现归并到同一边界，删掉常规 Windows 写入中重复的 ACL 子进程。保留不同备份、回滚版本、已有钥匙修复和自定义回调的保护。
- 删除 Router 内部另一个每五分钟目录定时器。之前只看 supervisor 的每日配置会漏掉这个实际定时器，因此“当前只有每日刷新”的早期判断已更正。
- 默认 doctor 排除未使用提供商的无关告警，保留有效 protocol variant、generic provider 和密钥池权威检查。
- 拒绝生成 POST 的隐式重定向，以及默认不确定运输重放；同时保留明确预发送恢复、受限语义修复和独立的凭据预检修复。

这里不能删去 Python 的重要实际条件是：当前 registry 还包含 `custom/qwen3.8-27b` 等 Chat 模型。只要该路由仍可调用，网关就仍是执行计划的依赖，即使菜单隐藏了它。减少常用 Responses 路径的一跳与删除整个 Python 进程是不同结果。

## 第三步：简化剩下的判断

引入共用的生成终态观察器，将 `completed / failed / incomplete / canceled / indeterminate` 与 HTTP 状态分开。失败的已知用量继续计量；历史行没有终态证据，保留旧解释并单独统计，不能事后“修正”为确定的成功或失败。桌面显示也消费同一语义。

共用执行计划解析最终模型协议，返回实际服务和路由指纹。运行 Router 与 API 服务固定采用启动时的选择；辅助视觉、压缩和故障切换不能越过这份选择读取尚未采用的候选配置。指纹不包含秘密值，也不宣称覆盖环境变量、Vertex 独立状态或覆盖文件的全部内容。

模型变化按“准备依赖 → 新进程准备路由 → 服务采用验证 → 新进程发布目录”执行。失败恢复原始文件后，再采用并发布原配置；取消和失败不能共享一个已过期的恢复截止时间。前台服务无法由后台管理器重载时，需要明确停止或重新启动，不能假装采用成功。

本次实际会话报错还暴露了协议假设过时：Router 只接受 `response.create`，而官方 Codex [2026-09-26 的实现](https://github.com/openai/codex/commit/12de0e395d3313bc564190d983cb4f5acf0be713) 会在 steering 时发送 `response.interrupt`。未捕获用户当时的具体控制帧，但旧代码拒绝语句、本机客户端二进制和本地失败对照共同确认了这一兼容性缺陷。修复立即处理控制消息，取消本地上游请求，以 `response.incomplete / interrupted` 结束当前响应，保留已完成内容和已观察用量。完成竞争、缓存溢出和已完成 JSON 写入背压都有对照；取消本地连接不证明远程执行或扣费已终止。

这项紧急兼容修复已单独通过三系统 CI，合并到个人仓库并部署为 `d161d2136cdb3f5b7e149eaa805ab8f72fa50329`；本机验证了中断识别、同连接续接和迟到中断不影响下一轮，未发出计费生成请求。其余优化仍作为独立候选审查，没有部署。

刷新原生目录只需要验证现有采用状态并发布，不需要每次安装依赖、重写网关或重启。并发刷新合并为单次运行，运行期间的事件保留一个后续检查。临时 Antigravity 待激活证明可能需要未选择提供商的监听器，但不产生可调用路由；它参与 readiness，不能让证明升级改变未变的路由指纹。

不可逆操作需要明确例外：OAuth 断开保留断开栅栏，不能恢复旧令牌使过时会话复活。环境变量密钥池只暂存元数据，必须经安装器持久化服务环境或重启前台进程后再 apply；不会提前发布客户端。

私有写入归并不只追求更快。测试发现临时文件的父目录被换成 junction 后，失败清理可能删除被重定向到的无关文件，因此清理只删除本次独占创建、身份仍一致的文件。这个检查没有声称消除恶意并发路径替换的全部出版风险。

## 第四步：缩短验证与故障定位周期

先跑能证伪假设的单项测试，再跑关联契约和全仓检查。使用真实本地 Router/API/模拟上游进程，而不是仅检查某函数被调用了几次。关键对照包括：完整接收 POST 后 reset、307 到拒绝连接、HTTP 200 内失败、配置写盘后进程未采用、隐藏 Chat 视觉模型、未使用端口已有无关服务、Windows 流式排空和私有文件替换失败。

新增 ingress、准备以及上游响应头等待分段。最后一项仍包含本地适配、网络和提供商处理，不能直接称为“模型耗时”。原有整个链路到响应头的指标保留兼容解释。

测量边界：七天日志共 5,857 次请求，原生 GPT-6.1 与 GLM 约占 98.1%，足以确定优化优先级；不能据此比较模型优劣。680 MiB 的进程 working-set 求和可能重复计算共享内存；55.7 秒启动间隔只是单次观察；三个私有写入微实验约 39% 改善只适用于该写入操作，不能宣传为端到端提升。

合并单位应是可独立验证的行为。真正需要同时改运行、安装、健康检查和发布的变更可以作为一个原子单位；无关输出修复、统计和文件写入优化应保持可单独审查的提交。审核应看负向对照能否失败，以及修复后原有能力能否保持，而非只看测试总数。

## 第五步：自动化已经验证过的流程

个人 fork 应对实际维护分支运行 CI，检查最终提交，而不是只测试另一个分支的相似代码。跨系统检查通过后再将状态检查设为合并条件。正式发布和本机替换要在独立阶段做；本次 fork 候选不能因为单机模拟测试通过就视为已经部署验证。

目录刷新自动化使用账户身份和客户端构建变化事件，身份摘要只在内存中存在；访问令牌轮换本身不代表账户变化，暂时缺少认证文件也不推断退出。每日检查仍有必要，因为服务器发布模型不必产生本地事件。网关秒级健康检查回答的是进程是否正在失效，不能用模型更新频率决定它是否必要。

不要自动缩短所有超时、无限重试、拉取模型或替换代理配置。自动化只应执行已经界定好的工作，且遇到不确定状态应给出具体失败证据。本次没有更改 FlClash、节点或生产网络。

## 验收状态及剩余边界

定向对照已验证输出保真、失败计量、默认运输不确定不重放、私有权限、计划驱动启动以及真实 Windows 排空。目录采用、凭据发布和停止流程在合并候选中继续接受全仓关联检查，最终结果以 PR 的具体提交和 CI 为准。

仍需区分而不能夸大的边界：客户端自身重试、其他适配器/密钥池/LiteLLM 的重试、明确的空输出修复、远程扣费是否终止、实际提供商的实时契约和不同系统的运行结果。模拟上游的重复执行证明本地策略可以重复提交，不能证明已经发生真实重复扣费或工具执行。

维护接口和可复现入口见 [运行契约](../maintenance/optimization-runtime-contracts.md)。生产部署前应在已确认的代码版本上另做小规模真实请求对照；此项尚未执行，不属于本次“先放个人仓库”的本机替换步骤。
